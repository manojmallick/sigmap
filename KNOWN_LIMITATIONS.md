# Known limitations

SigMap's benchmark claims are honesty-audited (measured grep-agent baseline, retrieval-tier proxies labeled as proxies, leakage-gated hard corpus). This page extends the same standard to the **extraction layer**: what each extractor tier actually does, where it truncates, and what that means for verification. Every claim here is checkable against the code.

Currently: **52 extractor modules covering 38 languages**. Counts are guarded against drift by `test/integration/known-limitations.test.js` (they must match `version.json`).

## Extractor tiers

| Tier | Languages | How it works | What it can miss |
|------|-----------|--------------|------------------|
| **1 — AST** | Python | Native CPython AST parse via `src/extractors/python_ast.py` when `python3` is on PATH: one process per run (`--batch`, 1,000 files each), not one per file ([#970](https://github.com/manojmallick/sigmap/issues/970)). Falls back to Tier-2-style regex when `python3` is absent, a batch fails, or the host's Python cannot parse the file (syntax newer than it) | With the fallback active: same gaps as Tier 2 |
| **1 — SCIP (opt-in)** | Any language with a SCIP indexer | `exactness.scip: true` reads a CI-produced `index.scip` at the repo root (import only) — compiler-typed signatures from `documentation` fences with definition-occurrence anchors, parsed by a zero-dep protobuf wire reader. Same per-file never-lose-vs-regex guard as the LSP tier; header labels `toolchain=scip:<tool>@<version>` on acceptance | No index, corrupt index, or file absent from it: same gaps as Tier 2. Index freshness is the CI pipeline's responsibility — a stale index is guarded per file by count, not by content |
| **1 — LSP (opt-in)** | C/C++ (measured) · Go, Rust (designed) | `exactness.lsp: true` asks a language server already on the machine (clangd/gopls/rust-analyzer or `exactness.lspServers` overrides) for documentSymbol; results cached per content hash + server binary. A per-file quality guard accepts the LSP result only when it does not lose surface vs the regex tier — a server parsing standalone can be macro-blind (clangd saw 7 of fmt/format.h's symbols). Header labels `toolchain=<server>@<version>` when used | Guard-refused or failed files: same gaps as Tier 2. Symbol detail strings are server-rendered and vary per server |
| **1 — AST (opt-in)** | TypeScript | `exactness.typescript: true` parses `.ts` with the TARGET repo's own `node_modules/typescript` (classic-API ≤5.x line; typescript@7's native compiler exposes no stable CJS API and falls back). Silent regex fallback; the generated header labels `toolchain=typescript@<version>` when active, so byte-stability is stated per toolchain version | Flag off or no usable typescript: same gaps as Tier 2. Hook return-shape sugar (`use*`) is regex-tier only |
| **2 — anchored regex** | JavaScript, TypeScript, Go, Rust, Java, Kotlin, Swift, PHP, Scala, Dart, PowerShell, Objective-C, C# (13), plus Astro and Vue/Svelte SFC script blocks, which route their `<script>` contents through the TS/JS path | Newline-preserving comment strip → declaration regexes → brace-depth block matching. Signatures carry `:start-end` line anchors; 7 languages (Python, JS, TS, Go, Rust, Java, PowerShell) also carry first-sentence doc-comment hints | Exotic declaration syntax the regexes don't cover (see gaps below); no type resolution — signatures are textual |
| **3 — pattern/heuristic** | Everything else — Ruby, **R**, **Lua**, **Elixir**, C/C++, GDScript, SQL, GraphQL, Terraform, Protobuf, shell, CI/pipeline definitions, config formats (YAML/TOML/XML/HTML/CSS/Markdown/properties/Dockerfile), and a generic fallback | Line-oriented pattern matching tuned per format | Anything structurally nested or syntactically unusual; no anchors, no doc hints |

**R, Lua and Elixir are Tier 3.** R in particular is a marketed capability — the README names it, `benchmarks/latest.json` says *"including R language"*, and there is a dedicated `benchmarks/R_LANGUAGE_BENCHMARKS.md` — so it is worth stating what that buys: declarations are extracted (`f <- function(a, b)`), but there are **no `:start-end` anchors and no doc hints**, because `name <- function(...)` is matched by line pattern rather than by a brace-depth scan. `get_lines` therefore cannot narrow to a symbol in these languages. Astro is Tier 2, not Tier 3: its frontmatter `<script>` contents route through the TS/JS path and do carry anchors.

**Recall is measured, not assumed, for Python and Ruby.** `node scripts/run-extraction-recall.mjs` asks CPython's `ast` and Ruby's Ripper what each file defines and counts how many of those names SigMap lists, for the extractor and for the index as shipped; floors are enforced in CI and every other language is listed as unmeasured. Results, method and the reference versions: [docs-vp/guide/extraction-recall.md](docs-vp/guide/extraction-recall.md).

All tiers are **deterministic** (same input → byte-identical output) and zero-dependency at runtime, with one qualification: the Python AST tier is deterministic *per Python version*. The interpreter decides which files parse (Django: 2,001 files on Python 3.9, 2,010 on 3.14), so a host with another Python, or none, extracts the same tree differently. The tier stays on by default, because it is the more accurate one, and the generated header names the interpreter that served it, `toolchain=python@3.9` (major.minor), as it does for the opt-in TypeScript tier; a run in which it served no file carries no label ([#970](https://github.com/manojmallick/sigmap/issues/970)). The xrepo gate still generates with `python3` shadowed, so its committed numbers do not depend on the host; `node scripts/run-xrepo-gate.mjs --python-ast` reports the Python repos on the default path beside them. There is no tree-sitter and no language server — that is a design constraint, not an accident, and it is exactly why the tiers above exist.

**Ruby is Tier 3 too, but it reads nesting.** It finds `class` / `module` at any indentation, lists each by the name the source gives it (`class BadRequest`, as the Python and Java extractors do, so a symbol lookup by that name finds it; the enclosing namespace is the `module` line above) and lists every `def` under the innermost class or module that owns it (`class << self` methods as `def self.x`, reopened classes merged, same-named classes in different namespaces kept apart). Ownership comes from block depth over source with comments, strings, heredocs, regexps and `%`-literals masked, not from a Ruby parser, so unusual constructs can still be misread. Like the other Tier-3 formats it has no `:start-end` anchors. Measured against Ruby's own parser (Ripper, Ruby 2.6, so modern syntax drops out of both sides) on 757 Rails and Sidekiq files with `node scripts/extraction-recall/ruby.mjs`: classes 944 of 944, modules 1,467 of 1,467, methods 7,196 of 7,292 by name, and 7,291 of 7,292 methods listed under the right owner; before nesting (#981) the same comparison gave 13.8%, 44.0%, 82.7% and 3.5%. The method figure leaves out operator and non-ASCII method names, which the extractor lists but that comparison does not match. The context file keeps only 25 signatures per file, so a large class loses its tail there; the index keeps up to 200 (see the truncation caps below).

## What the dependency graphs read

Extraction covers every language in the tier table above; the two dependency graphs read fewer of them, and a file in any other language contributes no edges.

| Graph | Used by | Reads |
|-------|---------|-------|
| **Import graph** | `--impact`, `get_impact`, the blast radius in `plan`, the ranker's neighbour boost | JavaScript/TypeScript, Python, Go, Rust, Java/Kotlin/Scala, Ruby, Elixir and R |
| **Method-level call graph** | `--callers`, `--callees`, `get_method_impact` | JavaScript/TypeScript, Python, Java, Go, Rust, Kotlin and Scala |

Everything else (PHP, C#, C/C++, Objective-C, Swift, Dart, Lua, GDScript, Vue, Svelte and Astro among them) has no edges. A blast-radius query on such a file answers `graph: unsupported-language` ("PHP imports are not tracked …") instead of "No importers found", `--json` carries `"graph": "unsupported-language"` with the language, and `--callers` on a symbol declared in one of them says where it is declared. An unknown symbol in a repo that holds unread files says how many were not searched. `sigmap doctor` counts the files the import graph cannot read, by language. None of these answers is evidence that nothing depends on the file. Extraction, ranking and `ask` are unaffected: they cover every language the extractors read.

## Truncation caps

There are three limits, and they are not the same thing (#982):

- **The generated context file keeps the first 25 signatures of a file** (`maxSigsPerFile`). The cut is silent: no notice is written, and the rest of the file is not in that artifact. A file with more than 25 top-level functions can hide a whole class that comes after them.
- **The retrieval index keeps up to 200 signatures of a file** (`maxIndexSigsPerFile`, never below `maxSigsPerFile`). `.context/sig-index.json` is never injected into a prompt, so it does not share the context file's token budget. It holds two lists per file: `files`, the first `maxSigsPerFile`, which is what ranking, `ask` and the tools that describe the context file (`read_context`, `list_modules`) have always read, and `more`, the rest, which the tools that look a symbol up read: `verify`, `verify-plan`, `search_signatures`, `explain_file`, `get_callee_signatures`, the call-graph's "not tracked" check and stack-trace squeezing. Ranking therefore does not change with the index limit. (One exception: with `python3` on PATH and a `maxSigsPerFile` above 30, the Python AST tier now returns the signatures it used to cut at 30, so Python files gain entries in `files` and in the context file.) Before #982 the index inherited the 25 and held 57-76% of Django's public symbols; the measured recall is on the [extraction recall](docs-vp/guide/extraction-recall.md) page. A run prints one line when a file went past the limit.
- **Most extractors stop at 200 signatures a file and 120 members a class**, on their own. Past 200 they end the list with `… +N more signatures` (`… +N more headings`, `keys` or `entries` for markdown, properties and TOML); past 120 members a class block ends with `… +N more methods`. The Python AST tier (`python_ast.py`) did the same at 30 until #982 and said nothing. The index drops the file-level notice line, which is a notice for a reader, not a signature, and the run's one-line summary counts those signatures as not indexed. The few extractors with no ceiling of their own (SQL, GraphQL, protobuf, Terraform and the generic fallback) are bounded at 1,000 a file. So a `maxIndexSigsPerFile` above 200 changes nothing for most languages and a god-file with more than 200 symbols (Django's `db/models/fields/__init__.py`) is still cut at 200.

Large god-files are therefore **under-represented in the context file by design** (the cap is what keeps the whole-repo map inside a model's context window), and **past 200 symbols in the index**.

## Known regex gaps (Tier 2)

- **Nested parentheses in parameter lists truncate at the first `)`** — `function f(a, b = g(x))` captures `(a, b = g(x` incorrectly. **Fixed for JavaScript, TypeScript, and PowerShell** by the shared balanced scanner (`src/extractors/scan.js`, G4 increment 1): params are depth-matched over string/comment-masked text, string defaults (including `)` or `//` inside quotes) survive intact, and type annotations strip depth-aware. The remaining Tier-2 languages (Go, Rust, Java, Kotlin, Swift, PHP, Scala, Dart, C#) still truncate — they migrate in later G4 increments, which remain the precondition for the arity-check verifier (D1).
- **PowerShell unexported functions treated as internal** — when an explicit export list is declared (`Export-ModuleMember` or `FunctionsToExport`), functions not listed are treated as internal module helpers and omitted from signatures. When no export list is present, all functions are emitted. Because omitted internal helpers do not enter the signature index, `verify` / `verify_suggestion` will report references to them as hallucinations (`fake-symbol`), and `closest-match` will suggest the nearest exported name.
- Multi-line declaration headers that break between the name and the parameter list can be missed entirely.
- Generic/type-parameter soup (deeply nested `<>`) is normalized textually, not parsed.

## What this means for `verify` / `verify_suggestion`

The Hallucination Guard builds its symbol index **from extracted signatures**. A real symbol that fell to the caps, sat in a file outside the detected source roots, or slipped past a Tier-2/3 regex is absent from that index — but `verify` does not stop there (#914). Before it reports a **`fake-symbol`** it looks the name up in the source, and drops it when the *code* of any file in the checkout calls or defines it (comments, strings and prose never count). What is still reported, at medium confidence, is a name the source neither calls nor defines — the point — and, as a conservative **false positive** rather than a silent pass, a real name that is defined only where the scan does not look: Lua, PowerShell, SQL and markup (their comments are not blanked), vendored, generated or excluded trees, files over 1.5 MB, or past the scan's deterministic 64 MB / 25,000-file budget. Mitigations in place: language/runtime builtin allowlists, closest-match suggestions on every flag, and confidence capped at `medium` for exactly this class of miss. Treat a medium-confidence symbol flag in one of those places as "check the file" rather than "the AI hallucinated".

Since the balanced scanner (v8.27) made JS/TS params exact, `verify` also runs **arity checks** (`arity-mismatch`, medium confidence) — but only where they can be trusted: uniquely-resolved top-level functions from exact-param languages (JS/TS + Python), non-variadic signatures, undotted calls. Method calls, ambiguous names, `...rest`/`*args` signatures, and every other Tier-2/3 language are deliberately not checked yet.

## Not limitations (frequently asked)

- **Byte-stability** — regenerating on an unchanged repo produces byte-identical output; drift is a bug, not an expectation.
- **Offline** — nothing here calls a network or an LLM.
- **Secret redaction** — signatures, `get_lines` output, evidence packs, and `sigmap redact` all pass through the same 10-pattern scanner; patterns are listed in the [CLI reference](https://sigmap.io/guide/cli#redact).
